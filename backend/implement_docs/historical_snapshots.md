# Исторические снимки в `sets_json`

24.06.2026

`sets_json` хранит факты прошлой тренировки. Значения, которые влияют на историю и аналитику, должны сохраняться как снимки на момент события, а не вычисляться из текущего состояния пользователя.

Главный кейс: `weight_composition` с собственным весом.

## Правило

- `cached_bodyweight_kg`, `cached_effective_kg` и `cached_display` — исторические снимки.
- При редактировании старого подхода UI должен получать собственный вес через `GET /user_weights/diary?end_date=<set_time>&limit=1`.
- Backend не должен перетирать существующий `cached_bodyweight_kg` последним весом из дневника.
- Backend может заполнить вес из дневника только если `source=user_bodyweight_history`, но `cached_bodyweight_kg` отсутствует.

## Зачем

Хочется иметь возможность **исправлять уже записанные тренировки задним числом**, не ломая правду того момента времени.

Если пользователь например забыл внести вес тела перед тренировкой, он может потом добавить измерение веса в дневник с датой “до подхода”, открыть старый подход и нажать **«Из дневника»**.
Тогда в подход должен попасть именно вес, актуальный **на момент этого подхода**, а не последний вес.

То есть `weight_composition` в `sets_json` должен быть **снимком состояния на момент выполнения**, а не динамической ссылкой на текущее последнее измерение!

Именно поэтому важно:

- при редактировании искать вес через `end_date=<время подхода>&limit=1`;
- сохранять `cached_bodyweight_kg` внутрь подхода;
- не перетирать этот `cached_bodyweight_kg` на backend при PUT/PATCH;
- позволять историю корректировать после факта, но так, чтобы аналитика и графики считались по восстановленной исторической реальности.

Это прям основа для нормальной аналитики: графики, тоннаж, прогресс и сравнения должны опираться на снапшоты, а не на “последнее известное сегодня”.
